00 — What this plan is actually working with

Context & constraints

Every decision below traces back to one of these facts. Worth reading before the phases, since it explains why the order is what it is.

The circuit is real, the data isn't (yet)

PB_001 → SP_001 → BM_001 → CY_001 mirrors an actual OCP grinding/classification line. You have no PLC/SCADA/historian access to it. What you do have — the flowsheet, the SysCAD dynamic simulation (Dynamic_Results.csv), and the %BPL/Cd granulometric curve — is the only ground truth for now, and it has to be treated as such: good enough to build and test the whole pipeline, not good enough to claim it reflects today's real plant state.

160 µm is the cyclone cut-point target OCP uses for ore quality; %BPL and Cd are OCP's own grade/contaminant classification metrics. These aren't arbitrary KPIs — they're the vocabulary the real operators already use, so the twin should speak it too.

Why monitoring comes before AI

Garbage in, garbage out: without real (or at least realistic, validated) sensor and failure history, any predictive-maintenance or optimization model would be trained on assumptions, not evidence. So the explicit order is: build a trustworthy, live-feeling pipeline and visualization first (monitoring) — then, once there's a track record of real or better-simulated data, revisit predictive maintenance and flow optimization.

This is why phase 08 (AI/ML) stays parked until phases 02–07 are working end to end.

Zero budget changes the tool list

The architecture diagram you shared uses HighByte, which is commercial. That gets replaced below with a free, self-hostable equivalent: Mosquitto + Node-RED instead of HighByte. Ignition stays, run as Ignition Maker Edition — free for non-commercial/educational use, full Perspective module, well above the tag count this project needs. Neo4j Community, BaSyx, Protégé, MinIO, React, Blender, three.js, n8n and AutoGluon are all already free — those stay as planned.

Two people, two operating systems

Docker Compose becomes the thing that makes "it works on my machine" irrelevant — every service (broker, database, storage, API) runs identically on Ubuntu and Windows. This was likely where the earlier attempt got messy without a plan; phase 02 below exists specifically to fix that before any visualization work resumes.

02

2D visualization

Ignition Maker Edition — the thing you tried before, this time with clean steps

Tasks, in order

  • Step 1 — install & commission: install the Ignition Gateway (Windows/Linux, same installer for every edition), commission it as Maker Edition, generate the free license from your Inductive Automation account
  • Step 2 — connect to the data: enable the MQTT Engine / OPC-UA modules and point Ignition at the Mosquitto broker from phase 01, subscribing to the CSV-replay topics
  • Step 3 — build the static view: redraw the flowsheet (PB_001, SP_001, BM_001, CY_001, six streams) as a Perspective view, no live bindings yet
  • Step 4 — bind one tag first: pipe color/opacity tied to %solids on one stream, prove the loop works end to end before wiring the rest
  • Step 5 — finish the bindings: flow animation, %BPL/P80 value call-outs, a color band on CY_001 showing how close the cyclone cut is to the 160 µm target, plus basic alarms
  • Step 6 — publish the Perspective session so it's viewable in a browser, ready to be embedded (iframe) in the React dashboard in phase 05

Maker Edition — what to keep in mind
Free, but personal/non-commercial/educational use only — fine for a study project, not for anything sold or run for a client later. It supports up to 10,000 tags and 10 concurrent Perspective sessions (nowhere near this circuit's needs), doesn't include the Vision module (Perspective covers this build fine), and needs a periodic internet check-in to keep the license valid. If offline operation ever matters more than that check-in, the alternative is the full unlimited-trial mode, which is functionally complete but restarts the gateway every 2 hours.

06

Predictive maintenance & flow optimization — parked

Revisit once phases 00–07 run cleanly on real or better data

You named these as goals 2 and 3, in that order, and were explicit that AI/ML shouldn't start before there's real data to avoid GIGO. This section is a placeholder for that future conversation, not a task list to start on now.

Do not start building
There's currently no failure/maintenance history and no real sensor stream — anything modeled today would be trained on assumptions. Wait until phase 00–05 are stable and either real plant data or a deliberately richer simulation exists.

Questions to answer when you get here

  • Predictive maintenance on which equipment first — BM_001 (highest-value asset) or SP_001 (simplest failure modes)?
  • What would "flow optimization" change in practice — setpoints, water addition, cyclone pressure? Whoever owns the answer to that should be part of that conversation.
  • Is there any way to get even informal maintenance logs from OCP (even anonymized/aggregated), or does the model have to be trained purely on simulated fault injection?
